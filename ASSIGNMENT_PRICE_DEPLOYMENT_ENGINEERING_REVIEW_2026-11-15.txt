ASSIGNMENT-DEPENDENT PRICE: CPU DEPLOYMENT ENGINEERING REVIEW
Date: 2026-11-15

DECISION
PASS the frozen engineering cost screens against the existing reference
runtime paths in both engineering initializations. Five equivalence/validation
test groups and the independent saved-artifact audit passed. No simulator or
research training was run. This clears a specific implementation cost obstacle;
it does not establish the thesis contribution, policy quality or novelty.
Before simulator integration, test similarly compiled reference paths and
repeat the paired comparison under a separately frozen deployment protocol.
Do not attribute an architecture advantage to different runtime compilers.

WHY THIS IMPLEMENTATION
Diagnostic profiling of the previous optimized route: 128 calls after 32
warmups on the original saved engineering checkpoint. Total instrumented time
0.029 s, module execution 0.017 s, tensor-to-NumPy conversions about 0.002 s,
native evaluation about 0.002 s. The remaining dominant measured region is
the scripted module path, not the coordinate sweep. These are instrumented
profile durations, not acceptance timings or a benchmark speedup denominator.

assignment_price_deployment_runtime.py moves the same neural network/head
equations into a CPU ONNX graph. FP32 neural/head arithmetic and FP64 head
outputs/coupled costs remain. Native code forms FP32 service workloads and
uses expm1 directly for pending work before FP64 conversion; it does not
replace expm1 with exp-minus-one. It reuses the prior validation/mask and
exact same native coordinate decoder, including stable vehicle order, retained
old-action ties, one fixed sweep, nonincrease check and selected full cost.
All four arms are supported. No training-model, reward, optimizer, threshold,
mask equation, tie rule or DDQN objective was changed. This is an immutable
exported snapshot requiring reconstruction after training weight changes.
The route combines graph heads and native decoder; it is not one monolithic
graph or a new optimal scheduler.

CORRECTNESS EVIDENCE
First four test groups passed; a separate extended test run passed all five.
Both reports and source versions are preserved. The extension checks the
specific near-zero and near-tie numerical risk of this execution backend.
- Four arms x two saved untrained checkpoints x 128 shared states = 1,024
  checks: exact action equality, head comparisons at rtol 1e-5/atol 1e-7,
  selected values at existing rtol 1e-5/atol 1e-6, unchanged source weights.
- 500 randomized and adjacent-FP32 mask-boundary/horizon checks against the
  original validation path.
- Nonfinite, terminal/off-grid, malformed task/workload and wrong shape/dtype
  rejections, plus noncontiguous valid inputs.
- Equal heads, returned-array ownership and snapshot independence from later
  mutation of source model weights.
- Adjacent-FP32 neural biases with zero, subnormal, tiny and larger queues:
  action equality and unchanged selected-value tolerance.
The old decoder retains its independent coordinate oracle and suboptimal
counterexample. Across graph/PyTorch backends, head values are numerically
close, not promised bitwise identical. Exact action equivalence is observed
on these fixtures, not proven on every possible near tie or learned model.
Trained checkpoint exports will need the same verification gates later.

INTERPRETATION AND NEXT GATE
There is now a small, fast engineering implementation of this proposed
mechanism against the frozen reference routes. The compared wide references
still execute their previous PyTorch/native route, whereas the new candidate
uses ONNX/native. This is useful implementation evidence but not a controlled
architecture-efficiency result. Apply the same compilation opportunity to
relevant references, verify action/value equivalence (especially near ties),
predeclare a single matched deployment comparison and audit its storage/full
latency results. Keep failed gates; do not weaken limits or select a favorable
initialization. No additional timing is authorized by this report itself.

Only after that engineering review should a temporary simulator fixture be
prepared. Then a prospective research protocol, fresh development seeds and
separate explicit research launch decision are required. Return/deadlines,
training/value stability, learned-price and sweep ablations and exact novelty
overlap remain open. No thesis claim revision or final phase is justified yet.
Word thesis and reserved final evaluation seeds remain unchanged. Security/
trust, cloud and charging remain outside contribution one's current branch.
